# AI Incident Copilot

### Intelligent IT Incident Detection, Similar Incident Search & AI Resolution Recommendation System

## 1. Problem Statement

IT operations teams deal with a constant stream of incidents (high CPU, database
timeouts, API errors, network issues, etc.). Engineers often spend a lot of time
manually figuring out:

- Is this incident actually abnormal, or just normal noise?
- What kind of incident is it?
- Has something like this happened before?
- What worked last time?

This slows down incident response, especially for less experienced engineers.

## 2. Proposed Solution

**AI Incident Copilot** is an AI-assisted decision-support dashboard that takes
incident/log data and automatically:

1. Detects whether an incident is anomalous (Isolation Forest)
2. Classifies the incident type (Random Forest)
3. Finds the most similar historical incident (Sentence Transformers + Cosine Similarity)
4. Generates a cautious, human-readable recommendation using an LLM (Groq), with a
   safe rule-based fallback if no API key is available

## 3. Objectives

- Automatically flag anomalous incidents from system metrics
- Classify incidents into categories (Database, Network, API, Server, Application)
- Retrieve the closest matching historical incident using semantic similarity
- Generate a probable-cause + recommended-action summary for engineers
- Present everything in a clean, professional Streamlit dashboard

## 6. Algorithms Used & Why

| Algorithm | Used for | Why |
|---|---|---|
| **Isolation Forest** | Anomaly detection | Works well on unlabeled, high-dimensional numeric data; doesn't need "anomaly" labels to train; fast and effective for outlier detection in system metrics. |
| **Random Forest** | Incident classification | Robust, hard to overfit, works well on small-to-medium tabular datasets, and gives clear feature importance / probability outputs. |
| **Sentence Transformers (all-MiniLM-L6-v2)** | Semantic embeddings of error messages | Captures the *meaning* of an error message, not just keywords, so "DB timeout" and "database connection failed" are recognized as similar. |
| **Cosine Similarity** | Comparing embeddings | Standard, efficient way to measure how close two embedding vectors are, regardless of their magnitude. |
| **LLM (Groq)** | Turning ML outputs into a readable recommendation | ML models give numbers and labels; the LLM turns that into a clear, human-readable, cautious explanation an engineer can act on. |

## 8. Dataset Description

A synthetic dataset of ~1000 IT incidents (`data/incidents.csv`), generated by
`generate_dataset.py`. Columns:

| Column | Description |
|---|---|
| incident_id | Unique ID (e.g. INC00001) |
| timestamp | When the incident occurred |
| cpu_usage | CPU usage % |
| memory_usage | Memory usage % |
| response_time | Response time in ms |
| error_count | Number of errors logged |
| network_latency | Network latency in ms |
| error_message | Human-readable error description |
| category | Database / Network / API / Server / Application |
| severity | Low / Medium / High / Critical |
| resolution | How a similar historical incident was resolved |

About 18% of records are generated with abnormal metrics so Isolation Forest has
real anomalies to detect, and each category has a distinct "metric signature" so
the classifier has genuine signal to learn from (not random noise).

## 10. Installation (Windows + VS Code)

1. Install Python 3.10+ from python.org (check "Add to PATH" during install)
2. Open the project folder in VS Code
3. Open a terminal in VS Code (`` Ctrl+` ``) and run:

```bash
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

4. (Optional) Copy `.env.example` to `.env` and add your Groq API key:

```bash
copy .env.example .env
```

Then edit `.env` and set `GROQ_API_KEY=your_key_here`. If you skip this step,
the app still works fully using the built-in fallback recommendation.

## 11. How to Run

```bash
python generate_dataset.py
streamlit run app.py
```

Then open the URL Streamlit prints (usually `http://localhost:8501`) in your browser.

## 14. Limitations

- Dataset is synthetic, not real production incident data
- Isolation Forest contamination rate is a fixed assumption (~18%), not learned
- Classifier uses only numeric metrics, not the error message text itself
- LLM recommendations are suggestions, not guaranteed root-cause diagnoses
- No authentication, persistence, or multi-user support (by design, for simplicity)

## 15. Future Enhancements

- Combine text features (error message) with numeric features for classification
- Real-time log ingestion instead of a static CSV
- Feedback loop where engineers confirm/correct AI suggestions to improve the model
- Multi-incident correlation (detecting related incidents happening together)
- Role-based access control and incident ownership tracking

## How to Explain This Project in an Interview

### 30-second explanation
"I built AI Incident Copilot, a tool that helps IT engineers triage incidents
faster. It looks at system metrics to flag anomalies, classifies what kind of
incident it is, finds the most similar past incident using semantic search, and
then uses an LLM to suggest a probable cause and next steps — all in a Streamlit
dashboard."

### 1-minute explanation
"The idea is that when an incident happens — say high CPU or a database timeout —
engineers usually have to manually dig through metrics and past tickets to figure
out what's going on. I automated that pipeline. First, an Isolation Forest model
looks at the incident's metrics (CPU, memory, response time, errors, latency) and
flags whether it's abnormal. Then a Random Forest model predicts what category the
incident falls into — Database, Network, API, Server, or Application. Next, I use
Sentence Transformers to turn the incident's error message into an embedding, and
cosine similarity to find the closest matching historical incident, along with how
it was resolved before. Finally, I feed all of that — the metrics, the anomaly
result, the category, and the similar past incident — into an LLM through the Groq
API, which generates a cautious, human-readable recommendation: a probable issue,
supporting evidence, and suggested next steps. If there's no API key, it falls back
to a rule-based recommendation so the app never breaks. Everything is shown in a
Streamlit dashboard with charts and incident drill-downs."

### Technical explanation
"The pipeline is: raw CSV → preprocessing (dedup, type fixing, missing value
handling) → Isolation Forest on standardized numeric features for unsupervised
anomaly detection → Random Forest classifier (trained with an 80/20 split,
evaluated with accuracy/precision/recall/F1) for supervised category prediction →
Sentence-Transformer (all-MiniLM-L6-v2) encodes error messages into dense
embeddings → cosine similarity retrieves the nearest historical incident → all of
that structured output is assembled into a prompt sent to Groq's LLM API, with
explicit instructions to use cautious ('probable', not 'confirmed') language, and
a deterministic Python fallback if the API is unavailable so the app degrades
gracefully instead of crashing."

### Q&A Prep

**1. Why did you choose Isolation Forest?**
It's built specifically for anomaly/outlier detection, doesn't need labeled
"anomaly" data to train (unsupervised), and scales well to multiple numeric
features like CPU, memory, latency, etc.

**2. Why Random Forest?**
It's robust to noise, doesn't need heavy feature engineering, resists overfitting
better than a single decision tree, and gives probability scores I can show as
"confidence" in the UI.

**3. Why Sentence Transformers?**
Keyword matching would miss that "DB timeout" and "database connection failed"
mean the same thing. Sentence embeddings capture semantic meaning, so similar
incidents are found even when the wording is different.

**4. Why Cosine Similarity?**
It measures the angle between two embedding vectors rather than their raw
distance, which makes it robust to differences in text length and is the
standard metric for comparing sentence embeddings.

**5. Why use an LLM?**
The ML models output numbers and labels (anomaly score, category, similarity %).
The LLM's job is to turn that structured information into a clear, readable
explanation and actionable recommendation for a human engineer.

**6. Why not use the LLM for everything?**
LLMs are slower, more expensive, and less reliable for structured numeric
tasks like anomaly detection or classification. Using dedicated ML models for
those tasks is faster, cheaper, more consistent, and more explainable — the LLM
is only used at the final "explain this to a human" step.

**7. How does anomaly detection work?**
Isolation Forest randomly partitions the data; anomalies are points that get
isolated in fewer splits than normal points, because they're "different" from
the bulk of the data. I standardize the features first so no single metric
dominates just because of its scale.

**8. How do you find similar incidents?**
Each incident's error message is converted into a numeric vector (embedding)
using a pretrained Sentence Transformer. Then I compute cosine similarity
between the current incident's embedding and every historical incident's
embedding, and pick the highest score.

**9. How is the probable root cause generated?**
It's generated by an LLM prompt that includes the incident's metrics, the
anomaly result, the predicted category, and the most similar past incident's
resolution. The LLM is explicitly instructed to use cautious language like
"probable issue" instead of claiming certainty.

**10. What are the limitations?**
The dataset is synthetic, the classifier only uses numeric metrics (not the
text), and the LLM's suggestions should always be verified by a human — it's a
decision-support tool, not an autonomous fixer.

**11. What would you improve in the future?**
Combine text and numeric features for classification, add a feedback loop
where engineers rate the AI's suggestions to improve future recommendations,
and support real-time log ingestion instead of a static CSV.
